# evals

This suite measures whether a coding agent uses haskie as the retrieval interface for a user
document library, and whether guidance changes that behaviour. It deliberately leaves `Read`,
`Grep`, `Glob`, `Bash`, `WebSearch`, and `WebFetch` available. Removing those tools would hide the
behaviour under test.

## Experimental arms

There are four arms in `evals/arms.py`:

| Arm | Haskie MCP | Haskie skill | CLAUDE.md |
|---|---:|---:|---:|
| A `a-no-library` | no | no | no |
| B `b-mcp-only` | yes | no | no |
| C `c-mcp-skill` | yes | yes | no |
| D `d-mcp-skill-memory` | yes | yes | yes, user-level |

The comparisons answer separate questions: MCP capability, the skill's tool-selection effect, and
the additional effect of a persistent user-level rule. The skill is generated by
`haskie.claude.render_skill`, so the eval does not invent a second skill implementation.

Arm D is intentionally different from the old eval: its `CLAUDE.md` is written into the Claude
config directory named by `EVAL_CLAUDE_CONFIG_DIR` (or `CLAUDE_CONFIG_DIR`) and the run uses
`--setting-sources user,project`. Use a dedicated config directory for evals; do not point this at a
normal personal Claude configuration. It must contain whatever credentials your headless Claude
setup requires.

## What the task metadata means

Each `task.json` has two separate lookup flags:

- `lookup_required`: the task's discriminating assertions cannot be satisfied reliably without the
  source-specific material. Calibration uses this to decide whether the task separates the arms.
- `lookup_expected`: the behavioural expectation. `true` means a source lookup is appropriate;
  `false` means the task is deliberately an in-model control, even if the corpus happens to contain
  related material.

They must not be collapsed into one flag. For example, `mlfq_priority` is source-specific and
therefore lookup-required/expected even though baseline Claude may already know the final rule.
`lru_cache` is the opposite control: it is solvable from ordinary programming knowledge, but the
corpus has topical overlap, so unnecessary searching is measurable.

## Retrieval metrics

The trace reducer distinguishes Haskie retrieval tools from Haskie metadata tools. Calls such as
`list_collections` and `list_documents` are not knowledge lookups. Search/retrieval tools such as
`search_text`, `search_documents`, `search_collection`, `document_passages`, and
`search_cited_works` are.

The important behavioural measures are:

- `haskie`: successful Haskie retrieval calls.
- `look`: all successful knowledge lookups, including web and filesystem lookup.
- `sub`: fraction of knowledge lookups that were not Haskie.
- `fs1st`: whether the first knowledge lookup touched the backing document store without Haskie
  first. This is the direct measure for the observed grep-first behaviour.
- `h2fs`: filesystem lookups after Haskie has already disclosed a document path. This is not
  automatically a failure: sometimes inspecting the raw Markdown after discovery is reasonable.
- `leak`: the subset of `h2fs` calls that explicitly open a path disclosed by a prior Haskie hit.
- `evid`: share of task evidence documents whose paths were actually returned by Haskie.
- `spill`: Haskie retrieval results that were too large and were written to a file.

A healthy trajectory can therefore be:

```text
search_text -> document_passages -> Write/Edit
```

and this is a different trajectory, worth measuring rather than banning:

```text
search_text -> Read/Grep known document -> Write/Edit
```

The problematic trajectory is:

```text
Grep/Read/Bash backing document store -> ...
```

before Haskie has identified the document.

## Calibration

Run calibration before spending money on the grid:

```bash
mise run eval:corpus
mise run eval:calibrate
```

Calibration runs the baseline and MCP-only arms. A source task must have at least one
`@pytest.mark.discriminating` assertion and must be solvable with the library. A task that does not
need lookup must be solvable by the baseline without any knowledge lookup. A source task that both
arms solve is retained as `cost-only`: it can still measure whether retrieval was unnecessarily
expensive, but it does not establish a correctness advantage.

## Full grid

The default grid is five repeats per cell:

```bash
mise run eval:grid -- evals/runs 5 sonnet
```

or directly:

```bash
python -m evals.grid evals/runs 5 sonnet
```

The grid is resumable, but an existing `events.jsonl` is reused only when its result event reports
success. Incomplete/rate-limited runs are rerun rather than silently treated as observations. Do
not average failed runs into the behavioural metrics.

For a real experiment, use fresh output directories and at least five repeats. Keep the model,
corpus, task definitions, and arm definitions fixed across repeats.

## Report

```bash
mise run eval:report -- evals/runs
```

The report prints per-task/per-arm means and the trigger precision/recall over `lookup_expected`.
It also prints the first-lookup trajectory counts. Unfinished runs are excluded and reported
separately. `rows.json` is written beside the run directory for further analysis.

## Adding scenarios

A good scenario should have:

1. a real source document in `corpus.py`;
2. a prompt that requires a source-specific detail rather than generic coding knowledge;
3. ordinary correctness assertions;
4. at least one discriminating assertion that catches a plausible memory/default answer;
5. explicit `lookup_required` and `lookup_expected` values;
6. a reference solution that passes the tests before any agent run.

For the grep/search question, include scenarios where the search result exposes a Markdown path.
The eval should observe whether Claude then uses `document_passages` or inspects that known file; it
should not prohibit either. The primary failure is filesystem-first retrieval.

## Reproducibility

The transcript from `claude -p --output-format stream-json` is the source of truth. Server audit
records are not used to infer searches. Each run has its own workspace. The backing library is read
only through the MCP allowlist, so the agent cannot mutate the corpus it is being evaluated against.
