# AGENTS.md

haskie turns personal documents into searchable collections, served over a Litestar API, a web
UI, and MCP. Every change serves the [mission](README.md#mission): fast, transparent, easy to
manage; relevant evidence without repeats; the agent reasons, haskie does the retrieval legwork.

## Project map

```
src/haskie/
  api/          routes, one module per feature; handlers marked mcp_tool= are also MCP tools
  document/     convert files to markdown, store them, render previews
  collection/   named sets of documents, one LanceDB index each
  indexing/     DBOS pipeline: chunk, embed, cache, index; model lifecycle
  search/       retrieval, passages, near-duplicate folding, sessions
  claude_code/  skill and rule files installed into Claude Code
  app.py        Litestar app; cli.py the CLI; claude.py the Claude Code install
  settings.py   settings; db.py SQLite; home.py ~/.haskie; cpu.py the CPU budget
tests/          by area: flat test_*.py plus document/, indexing/, search/
docs/           one page per topic, with diagrams; update it when behavior changes
web/            React + TypeScript UI (Bun)
design/         HTML mockups and design.css, which web/ imports
mise/tasks/     one executable file per task
```

## Commands

Run everything through `mise run <task>`, never the underlying tool. Main ones: `setup`, `dev`,
`check` (`--fix`), `test`, `schema`, `build`. [CONTRIBUTING.md](CONTRIBUTING.md) lists every task
and the design decisions.

A change is done only when `check` and `test` pass. A new task is a new file in `mise/tasks/`
with `#MISE description="..."` and `set -euo pipefail`. Order tasks with `#MISE depends=[...]`,
not hand-rolled process control. Never add an inline entry to `mise.toml`.

## Code style

- Python 3.13: `ruff` (line length 100), `ty`, async Litestar, `msgspec.Struct`, `structlog`.
- Frontend: `oxlint`, `tsc`. `web/src/schema.d.ts` is generated by `mise run schema`. Never edit
  it, never hand-write a type it covers.
- Comments explain only the non-obvious why.

## How to work

- **Fix the cause, not the symptom.** Choose the proper solution, and refactor when the clean fix
  needs it. Never dodge a structural problem with a special case, flag, or workaround. If the
  proper fix is out of scope, say so and name it.
- **Test rigorously and holistically.** Cover every branch and edge the change touches. Test
  through real entry points (API, CLI, pipeline) as well as units. Use real payloads, put tests
  beside their neighbors, and assert what changed.
- **Prove, don't assume.** Read the code before reasoning about it. Treat every claim about
  behavior, performance, or a library as a hypothesis, and confirm it with a test, script, or
  measurement before acting. Report what you verified and what you did not.

## Commit subjects and the version

The squashed PR title is the commit subject on `main`, and it decides the next version. Write
`<type>[(<scope>)][!]: <subject>` with type `majorfeat`, `feat`, `fix`, `perf`, `refactor`,
`docs`, `test`, `build`, `ci`, `chore`, `style`, or `revert`.

- `majorfeat!` is major, `feat` or `feat!` is minor, anything else is patch.
- `!` elsewhere only marks a breaking change. `majorfeat` without `!` fails `mise run bump`.
